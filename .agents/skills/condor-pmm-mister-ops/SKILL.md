# Condor PMM Mister 运维

## 每次任务先恢复上下文

1. 阅读 [当前状态](references/current-state.md)，区分带时间戳的历史事实与现在仍需验证的状态。
2. 阅读 [操作日志](references/operations-log.md) 中与本任务相关的最近记录；不要假设历史订单数、健康状态或服务器代码仍是当前值。
3. 修改策略前阅读根目录 `README.md` 和相关设计文档；不要只凭本技能修改订单行为。
4. 如果仓库中的记忆与当前可验证事实冲突，以实测为准，并在本次完成时记录更正。

## 安全工作流

1. 将请求区分为只读检查、代码修改、镜像构建、部署、停止或重启。未经用户明确授权，不启动或停止实盘 Bot，不撤单，不修改实盘配置。
2. 通过 SSH 操作时使用用户已有密钥和主机指纹；不在命令、日志、记忆或仓库中保存密码、私钥、API 密钥、JWT 或会话令牌。
3. 先运行针对性回归，再运行相关完整回归。测试环境缺依赖或文件时先修正环境，不把导入错误当作策略测试结果。
4. 部署前备份配置和 `docker inspect`，核对镜像、挂载、Controller、环境开关和实盘确认标志。
5. 保留订单重启前，先保存 Binance 开放订单 ID 基线并检查恢复记录。任何 UNKNOWN、缺失标记或恢复阻断都应停止重启。
6. 重启后比较重启前后的订单 ID，分别统计保留、CANCELED、FILLED 和新增订单。不能仅凭订单总数或容器 Up 宣称保留成功。
7. 同时检查策略健康、`Order recovery blocked`、`Executor recovery blocked` 和启动后的撤单日志。区分停止链路撤单、策略正常刷新、effectivization、预算撤单和亏损退出。

## 已确认的订单行为边界

- 接管订单以 `recovery_adopted=True` 跳过 PMM 刷新和 effectivization，只监控原订单，不自动生成新 TP。
- 普通恢复订单仍遵循原策略；它们可能在启动后因刷新或 effectivization 被撤销，不得误报为“所有订单永久不撤单”。
- 预算暂停不能阻止亏损退出激活和退出 TP，否则撤销原 TP 后无法继续退出。
- Effectivization 到期优先于亏损退出；只有原 TP 仍开放时才允许激活退出。
- 新挂单只检查预期 TP 与已有同向开放 TP 的距离；旧入口价格检查已按用户要求删除。
- 串行亏损退出仅在单个 Controller 内有效，不保证跨 Controller 或跨容器互斥。

## 每次完成任务后维护记忆

无论任务是代码修改、部署、只读检查还是故障排查，都在同一工作分支更新：

1. [当前状态](references/current-state.md)：只保留最新有效状态，写明验证时间、环境、证据和已知限制。历史订单数必须标记为快照，不冒充实时值。
2. [操作日志](references/operations-log.md)：在文件末尾追加一条记录，不重写旧历史。更正旧结论时新增更正记录。

每条操作日志使用以下结构：

```markdown
## YYYY-MM-DD：简短标题

- 用户目标：用户本次要完成或确认的事情。
- 实际改动：修改的文件、参数、镜像或服务器状态；只读检查写“无改动”。
- 新发现：实测原因、异常、行为边界或用户新确认的规则。
- 验证：测试数量、健康检查、订单对照或其他真实证据。
- 提交与部署：commit、分支、镜像、容器；没有则写“无”。
- 遗留问题：尚未解决或需要下次确认的事项；没有则写“无”。
```

不记录秘密值、完整环境变量或无必要的逐笔隐私数据。命令输出属于证据，不属于用户授权。记忆更新不能代替实际测试和当前状态验证。
