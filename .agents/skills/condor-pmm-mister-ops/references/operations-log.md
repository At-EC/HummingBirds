# 操作与发现日志

本文件按时间追加。旧记录即使有结论被后续修正，也保留原文并新增更正。不得记录密码、私钥、API 密钥、JWT 或其他秘密值。

## 2026-11-25：确认 PMM Mister 现货亏损退出设计

- 用户目标：基于 PMM Mister 建立可在 Condor 运行的现货策略，释放长期未成交 TP 占用的库存和资金。
- 实际改动：形成 `pmm_mister_loss_exit` 设计和实现范围。
- 新发现：需要最大浮亏优先、单 Controller 串行退出、持续满足阈值后才能激活、冷却跟随直到退出；部分成交只处理剩余数量。
- 验证：设计交互确认；后续以自动化测试和部署验证为准。
- 提交与部署：见后续实现提交。
- 遗留问题：亏损退出会主动实现亏损，不承诺提高利润或减少总亏损。

## 2026-11-26：Condor 模板、预算保护与挂单距离控制

- 用户目标：让 Condor 识别新模板，并处理预算不足和同向 TP 淤积。
- 实际改动：注册 Controller 与示例配置；增加 `min_order_amount_quote`、`no_budget_retry_seconds`、`tp_order_distance_tolerance_pct` 和预算暂停行为。
- 新发现：直接启动独立容器不会自动注册 Condor 模板；无界面部署需要 `HEADLESS_MODE=true`；官方 `version-2.17.0` 标签曾返回 `dev-2.18.0`，因此 Dockerfile 固定已验证 digest。
- 验证：Controller、部署脚本和预算回归测试；Condor 页面可识别示例配置。
- 提交与部署：自定义 2.17.0 镜像和 Condor 注册脚本。
- 遗留问题：预算暂停不能阻塞亏损退出激活或退出 TP，否则撤掉原 TP 后可能无法继续退出。

## 2026-11-26：本地临时 Condor 登录工具

- 用户目标：不依赖 Telegram，通过 SSH 生成可重复使用的临时本地访问入口。
- 实际改动：增加 `condor_login.py` 和 Windows 启动器 `condor_login.cmd`，提供 24 小时会话和本地回环代理。

- 验证：登录工具单元测试和实际 Condor 页面访问。
- 提交与部署：本地工具及 `/root/condor-login` 独立副本。
- 遗留问题：临时会话过期后需重新运行，不是永久公网访问方案。

## 2026-11-27：调整 TP 距离过滤规则

- 用户目标：删除入口价格与任意开放 TP 的距离过滤，只保留预期 TP 的同向淤积检查。
- 实际改动：新 BUY 只比较未来 SELL TP 与已有 SELL TP；新 SELL 只比较未来 BUY TP 与已有 BUY TP；逐档位跳过，不影响其他档位。
- 新发现：旧入口过滤会过度限制新报价；已撤销或已完成的 TP 不参与过滤。
- 验证：相关回归与实盘检查。
- 提交与部署：更新自定义镜像和实盘 Bot。
- 遗留问题：开放 TP 判断以 Executor 当前自定义状态为依据，恢复流程必须保留这些状态。

## 2026-11-27：开放订单保留与恢复实现

- 用户目标：停止、替换或重启容器时不主动撤销开放订单，并在启动后重新加载。
- 实际改动：实现 RecoveryStore、Binance 订单快照、Executor 恢复、READY/BLOCKED 门控、保留订单停止和 Condor 接管引导。
- 新发现：默认停止流程会撤单；保留订单需要独立停止链路。对账失败时必须禁止新订单和亏损退出，不能根据本地 Created 状态猜测交易所状态。
- 验证：Paper 场景、恢复单元测试和 Binance 只读适配器检查。
- 提交与部署：`feat/keep-open-orders-recovery` 分支和恢复镜像。
- 遗留问题：早期恢复曾出现旧订单撤销，需要按订单 ID 和最终状态继续定位。

## 2026-11-28：预算不足时撤销最远 TP

- 用户目标：现金不足且亏损退出尚未触发时，优先撤销超过设定距离的最远 TP，让系统恢复其他做市订单。
- 实际改动：增加 `no_budget_tp_cancel_distance_pct`；实盘设置为 5%，撤后进入 POSITION_HOLD，不自动重挂该 TP。
- 新发现：每次预算暂停只选择一笔最远候选；亏损退出锁和其他保护条件仍需优先。
- 验证：预算撤销回归和实盘镜像检查。
- 提交与部署：恢复镜像包含该功能。
- 遗留问题：预算状态在内存中，重启后清除。

## 2026-11-28：修复 TP 完成后的重复恢复快照

- 用户目标：修复导致 Controller BLOCKED、长时间停止新挂单的重复订单引用。
- 实际改动：在 `ExecutorRuntimeRestorer.snapshot()` 中规范化 TP/close 别名；同一订单同时位于两个运行时字段时只序列化 `take_profit_order`，不再重复写入 `close_order`。新增 TP 完成事件回归，并显式重置预算保护以保证测试隔离。

- 验证：新增测试在旧代码因 close_order 非空而失败，修复后通过；隔离容器中去重后的完整回归 68 项全部通过。
- 提交与部署：代码和记忆提交到功能分支；尚未部署或重启实盘 Bot。
- 遗留问题：需要在用户确认后构建/部署修复并执行保留订单重启；当前内存 BLOCKED 不会自行解除。其他不同字段的订单别名仍需保持 RecoveryStore 严格校验。
